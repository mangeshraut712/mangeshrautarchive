# Software Engineering Best Practices for Long-Term Success

> **Standard:** Engineering Architecture & Quality Blueprint  
> **Last updated:** 2026-09-08

## Overview

This document codifies the 14 core software engineering principles that govern development, architecture, testing, and lifecycle maintenance across this repository. Every contribution—whether human-authored or generated by autonomous AI agents—must adhere to these practices to guarantee long-term maintainability, reliability, and architectural clarity.

### 1. Explicit Architecture

_Choose an explicit architecture (layered, MVC, modular services) that matches the product’s scale, and keep it documented so new work has a place to live._

- **Repository Implementation:** The portfolio follows a strict layered topology:
  - **Static Presentation Layer:** Vanilla HTML5, Apple HIG CSS custom properties, and native ES modules (`src/`).
  - **Edge / API Layer:** Cloudflare Worker edge proxy (`assistme-chat.workers.dev`) and FastAPI serverless backend (`api/routes/`).
  - **Tooling & Build Layer:** esbuild bundling, SVG synthesis, and health runners (`scripts/`).
- **Standard:** Every new feature, endpoint, or utility must be placed in its designated layer. Cross-layer leakage (e.g., embedding backend secrets into static bundles or mixing API business logic into UI event listeners) is strictly forbidden.

---

### 2. Loosely Coupled Modules

_Split the system into loosely coupled modules with one clear responsibility each, so change in one area does not ripple through the rest._

- **Repository Implementation:**
  - Frontend modules under `src/js/modules/` (e.g., `theme.js`, `chatbot.js`, `sound-effects.js`, `travel-page.js`) expose clean, isolated interfaces and communicate via DOM events or pub/sub rather than direct shared mutable state.
  - Backend routes under `api/routes/` (`chat.py`, `monitoring.py`, `integrations.py`) operate independently with zero cyclical imports.
- **Standard:** Changes to the chat streaming protocol must not break the music widget; updating travel map markers must not alter systems telemetry.

---

### 3. Design for Scalability & Growth

_Design for growth from the start: isolate stateful parts, keep interfaces stable, and plan how the system will scale horizontally and vertically._

- **Repository Implementation:**
  - **Stateless Compute:** All serverless functions in `api/` are stateless, allowing automatic horizontal scaling across Vercel and Cloudflare Edge runtimes.
  - **Isolated Persistence:** Session data, rate limits, and analytics are isolated to Redis, Supabase, and localStorage adapters rather than in-memory global state.
  - **Stable Schema Contracts:** API request/response payloads are validated via Pydantic v2 schemas (`api/models.py`), ensuring backward compatibility across frontend updates.

---

### 4. Self-Documenting Naming

_Name variables, functions, types, and modules so the intent is obvious without extra commentary._

- **Repository Implementation:**
  - Variables reflect semantic meaning: `hasActiveStreamingSession`, `retryCountWithBackoff`, `isMobileViewport`, `maxAllowedDiffPixels`.
  - Function names lead with clear verbs: `calculateTokenBurnRate()`, `assertNoHorizontalOverflow()`, `hydrateKeynoteStage()`.
  - Constants are strictly screaming-snake-case: `MAX_STREAM_TIMEOUT_MS`, `APPLE_BLUE_HEX`, `CHANGELOG_REPO`.
- **Standard:** If a function or variable requires a comment simply to explain _what_ it is, rename it. Comments should be reserved for _why_ a specific constraint or edge case exists.

---

### 5. Simple, Readable Control Flow

_Prefer simple, readable control flow over clever or dense logic; complexity should be justified by a real constraint._

- **Repository Implementation:**
  - Avoid deeply nested ternaries, convoluted regex lookarounds, and premature meta-programming.
  - Use early returns / guard clauses at the beginning of functions to handle boundary conditions, errors, and uninitialized state:
    ```javascript
    if (!stage || !deckContainer) return;
    if (activeTag === 'input' || activeTag === 'textarea') return;
    ```
- **Standard:** Readability for future maintainers and automated agents takes precedence over micro-golfed syntax.

---

### 6. Small, Single-Purpose Functions

_Keep functions and methods small and single-purpose so they can be reasoned about, tested, and reused._

- **Repository Implementation:**
  - Functions adhere to the Single Responsibility Principle (SRP). UI rendering (`renderWritingCard()`), data formatting (`formatTokenCount()`), and event binding (`bindKeynoteListeners()`) are cleanly segregated.
  - Functions exceeding 50 lines are reviewed for extraction into focused helper utilities.

---

### 7. Enforced Repo-Wide Style & Formatting Standards

_Enforce one formatting and style standard across the repository so reviews focus on behavior, not noise._

- **Repository Implementation:**
  - **JavaScript:** ESLint 10 with strict flat config (`eslint.config.js`), single quotes, 2-space indentation, semicolons, and zero warnings.
  - **CSS:** Stylelint 17 (`.stylelintrc.json`) enforcing Apple HIG properties and order.
  - **Python:** flake8 with 120-character line limit and strict vulture dead-code elimination.
  - **Formatting:** Prettier (`.prettierrc`) executed pre-commit to guarantee zero whitespace or indentation diffs.

---

### 8. Document Architecture, APIs & Invariants

_Document architecture, public APIs, and non-obvious invariants so the system remains understandable years later._

- **Repository Implementation:**
  - **[`docs/STRUCTURE.md`](docs/STRUCTURE.md):** Complete directory tree and subsystem map.
  - **[`docs/DESIGN.md`](docs/DESIGN.md):** The Apple HIG liquid glass design system and specular metallic shine rules.
  - **[`docs/API.md`](docs/API.md):** REST and streaming NDJSON endpoint specifications.
  - **[`AGENTS.md`](AGENTS.md):** Standardized instructions and runtime constraints for autonomous coding agents.

---

### 9. First-Class Automated Testing

_Write code that is testable at unit, integration, and end-to-end levels, and treat tests as part of the product, not an afterthought._

- **Repository Implementation (414+ Total Automated Tests):**
  - **Unit Tests:** 239 Vitest tests (`tests/unit/`) validating DOM helpers, Markdown rendering, edge cache contracts, and data models in sub-second execution.
  - **API Tests:** 175 pytest tests (`tests/api/`) verifying FastAPI endpoints, security headers, rate limits, and streaming responses.
  - **E2E Tests:** Playwright multi-browser test matrix (`tests/e2e/`) running across 16 device configs (Desktop Chrome/Safari/Firefox, iPhone, iPad, Pixel) enforcing 0 horizontal overflow and UI state fidelity.

---

### 10. Continuous Refactoring

_Refactor regularly to improve structure and clarity without changing external behavior._

- **Repository Implementation:**
  - Regularly consolidate duplicated CSS into shared design tokens (`--apple-blue`, `--glass-bg`).
  - Upgrade deprecated libraries and prune unused utilities before technical debt compounds.
  - Back every refactoring pass with passing unit and E2E regression tests before merging.

---

### 11. Intentional Technical Debt Paydown

_Track and pay down technical debt on purpose; do not let shortcuts become the architecture._

- **Repository Implementation:**
  - Cross-page content duplication, temporary mock fallbacks, or densified style overrides are tracked in `changelog-entries.js` and systematically addressed.
  - "Temporary fixes" must include a clear remediation path or issue reference; they are never allowed to silently solidify as permanent architecture.

---

### 12. Reviewable Git History

_Use Git with a clear branch and merge policy so history stays reviewable and recoverable._

- **Repository Implementation:**
  - **Conventional Commits:** `feat(...)`, `fix(...)`, `style(...)`, `chore(...)`, `docs(...)` with descriptive scope.
  - **Observability:** Every release commit documents the active engineering model, purpose, and metrics.
  - **Clean Trees:** All merges to `main` maintain linear, bisectable history with atomic commits.

---

### 13. Rigorous Code Reviews

_Require code reviews to protect quality, share design knowledge, and catch defects before they ship._

- **Repository Implementation:**
  - Automated PR checks block unformatted code, lint regressions, or failing unit/API tests.
  - Architectural changes undergo multi-agent verification and explicit review gates before deployment.

---

### 14. Fully Automated CI/CD

_Run CI/CD so every change is built, tested, and released through the same automated path._

- **Repository Implementation:**
  - GitHub Actions workflow (`.github/workflows/deploy.yml`) runs on every push:
    1. Workflow linting (`actionlint`) and secret leak scanning.
    2. Node and Python dependency installation with lockfile integrity.
    3. Full test suites: ESLint + Stylelint + Prettier + 239 Vitest + 175 pytest.
    4. Production esbuild bundle compilation and asset cache-busting.
    5. Lighthouse CI deployment gates enforcing **100/100/100/100** score thresholds on built output.
    6. Automated static deployment to GitHub Pages.
- **Rule:** No code is manually deployed or published outside the unified CI/CD pipeline.
